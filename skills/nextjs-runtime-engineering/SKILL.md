# Next.js runtime engineering

Use this skill to work on a Next.js application the way the installed version expects, not the way older training data remembers. The core idea: read the docs that ship with the installed `next` package, observe the running dev server through its MCP endpoint, make the smallest correct change, and prove it with typecheck, tests, a production build and a browser regression run.

## When to use

- Fixing runtime, compilation, hydration or routing errors in a Next.js 16+ project.
- Adding or changing App Router routes, layouts, route handlers, server actions or caching behavior.
- Migrating code to async request APIs, Turbopack or Cache Components.
- Investigating why something works in `next dev` but fails in `next build` or on Vercel.

## When not to use

- Pages Router-only projects on Next.js 12 or older: follow that project's own docs instead.
- Pure styling or motion work with no framework behavior involved: use `motion-systems` or `gsap-motion`.
- 3D scene internals: use `react-three-fiber` or `threejs-production`, and return here only for the Next.js integration boundary.

## Compatible versions

Verified 2026-10-22 via npm registry/official docs.

| Package / service | Version or endpoint | Notes |
| --- | --- | --- |
| `next` | 16.4.2 (latest) | App Router, Turbopack is the default bundler |
| `react`, `react-dom` | 19.x | Required by Next.js 16 |
| Dev server MCP | `http://localhost:<port>/_next/mcp` | Exposes errors, routes, logs and compilation issues |
| `next-devtools-mcp` | 0.4.0 | Thin bridge that discovers and connects to the running dev server |
| Vercel MCP | `https://mcp.vercel.com` | OAuth; only reviewed and approved clients are supported |
| Bundled docs | `node_modules/next/dist/docs/` | Version-matched to the installed package |

Always prefer the resolved version in the lockfile over this table.

## Architecture patterns

Async request APIs. In Next.js 16, `params`, `searchParams`, `cookies()` and `headers()` are asynchronous and must be awaited.

```tsx
// app/products/[slug]/page.tsx
type Props = { params: Promise<{ slug: string }>; searchParams: Promise<{ tab?: string }> };

export default async function Page({ params, searchParams }: Props) {
  const { slug } = await params;
  const { tab } = await searchParams;
  return <ProductView slug={slug} tab={tab ?? "overview"} />;
}
```

Client boundaries. Keep `'use client'` at the leaf that needs state, effects or browser APIs. `dynamic(..., { ssr: false })` is only allowed inside a client component.

```tsx
// components/scene-shell.tsx
"use client";
import dynamic from "next/dynamic";

const Scene = dynamic(() => import("./scene"), {
  ssr: false,
  loading: () => <div className="scene-placeholder" aria-busy="true" />,
});

export function SceneShell() {
  return <Scene />;
}
```

Route handlers.

```ts
// app/api/health/route.ts
export async function GET() {
  return Response.json({ ok: true });
}
```

Agent MCP configuration (`.mcp.json`). Pin the bridge version rather than tracking `@latest` in shared configuration.

```json
{
  "mcpServers": {
    "next-devtools": { "command": "npx", "args": ["-y", "next-devtools-mcp@0.4.0"] }
  }
}
```

Projects generated by recent `next dev` may contain an `AGENTS.md` block telling agents to read `node_modules/next/dist/docs/` before writing code. Treat it as a binding project instruction.

## Workflow

1. Inspect `package.json` and the lockfile. Record the resolved `next`, `react` and TypeScript versions and whether the project uses the App Router, Pages Router or both.
2. Read the relevant guide in `node_modules/next/dist/docs/` for the feature you are touching. Note deprecation notices.
3. Start the dev server (`next dev`) and confirm it serves the affected route.
4. Query runtime state through `/_next/mcp` directly, or through `next-devtools-mcp`, to list current errors, routes, logs and compilation issues. Capture the exact error text.
5. Locate the responsible code with semantic symbol search (Serena or the host agent's native LSP/search) instead of broad text grep where possible.
6. Make the minimal fix on a feature branch. Do not refactor unrelated files or change caching semantics silently.
7. Run typecheck (`tsc --noEmit`), the project's tests and `next build`. Fix any build-only failure; do not treat a passing dev server as proof.
8. Run a Playwright regression of the affected routes (see `playwright-browser-qa`), including console error capture.
9. Produce a preview build or Vercel preview deployment and inspect it.
10. Request explicit user approval before any production deployment or Vercel write action.

## Dev versus build differences to check

- Static rendering versus dynamic rendering: a route that reads cookies or headers becomes dynamic.
- Caching: Cache Components and fetch caching can hide stale data in production that dev never shows.
- Environment variables: only `NEXT_PUBLIC_` variables reach the client bundle, and they are inlined at build time.
- Server-only modules imported into client components fail at build time even if dev tolerates them briefly.
- Turbopack and webpack configuration differ; custom webpack config may not apply under Turbopack.

## Performance requirements

- Keep heavy client libraries (3D, charts, editors) behind dynamic imports with a reserved layout box.
- Avoid marking whole layouts `'use client'`; push the boundary down.
- Use `next/image` with explicit dimensions or `fill` plus a sized parent to prevent layout shift.
- Check the build output for unexpectedly large client chunks after each change.

## Accessibility

- Preserve semantic landmarks in layouts and a single `h1` per page.
- Loading and error boundaries (`loading.tsx`, `error.tsx`) must announce state in readable text, not only spinners.
- Client navigation must keep focus management sensible; verify keyboard flow after route changes.

## Security & permission boundaries

- Never print or commit `.env*` contents, tokens or Vercel credentials.
- Route handlers and server actions must validate input on the server.
- The dev server MCP endpoint is local development tooling; never expose it publicly.
- Vercel MCP write actions (deploy, env changes, domain changes) require explicit user approval in the same session.
- Do not push, publish or promote a deployment without separate authorization.

## Failure cases & fixes

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `params` used without await, type error or runtime warning | Next.js 16 async request APIs | `await params` / `await searchParams` / `await cookies()` |
| `ssr: false is not allowed with next/dynamic in Server Components` | Dynamic import in a server component | Move the dynamic import into a `'use client'` wrapper |
| Hydration mismatch | `Date`, `Math.random`, `window` or locale formatting during render | Move to effect, pass deterministic props, or render client-only |
| Works in dev, fails in build | Server-only import in client tree, type error, or prerender failure | Read build log, split server/client modules, fix types |
| Stale data in production | Caching defaults or Cache Components | Review caching docs in bundled docs; set explicit revalidation |
| `next-devtools-mcp` cannot find server | Dev server not running or different port | Start `next dev`, confirm port, retry discovery |
| Vercel MCP refuses connection | Client not on approved list or OAuth missing | Use Vercel dashboard/CLI with user consent; report the gap |

## Verification criteria

- [ ] Resolved `next` and `react` versions recorded from the lockfile.
- [ ] Relevant bundled doc file path cited for each framework API changed.
- [ ] Dev server MCP reports zero errors for the affected routes after the fix.
- [ ] `tsc --noEmit` exits 0.
- [ ] Project tests pass.
- [ ] `next build` exits 0.
- [ ] Playwright regression passes with no console errors on affected routes at 1440, 768 and 390 px widths.
- [ ] Preview deployment inspected; production deployment only after explicit approval.
